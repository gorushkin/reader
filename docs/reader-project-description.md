# Reader — описание проекта

## 1. Назначение

Reader — небольшой самостоятельный сервис и клиент для чтения электронных книг.

На текущем этапе проект сфокусирован не на библиотеке, продаже книг, авторах или издательской платформе, а на самой механике чтения:

- получение контента книги;
- отображение структурированного текста;
- пагинация под размеры экрана;
- переход между страницами;
- переход между чанками;
- сохранение и восстановление позиции чтения;
- дальнейшая поддержка offline-first сценария.

Главная техническая задача первого этапа — построить удобное постраничное чтение без вертикального скролла.

---

## 2. Текущий scope

В scope проекта входят:

1. Модель контента книги.
2. Получение книги целиком или отдельными чанками.
3. Рендеринг HTML или структурированных блоков.
4. Горизонтальная пагинация под текущий viewport.
5. Навигация вперёд и назад.
6. Определение количества визуальных страниц.
7. Сохранение логической позиции в книге.
8. Пересчёт раскладки при изменении параметров отображения.
9. В дальнейшем — локальное хранение книг и offline-режим.

Пока не входят в scope:

- социальные функции;
- публикация и продажа книг;
- кабинет автора;
- комментарии и обсуждения;
- рекомендации;
- полноценная DRM-система;
- сложная синхронизация между устройствами.

---

## 3. Базовая модель книги

Книга рассматривается как упорядоченный поток контента.

Упрощённо:

```text
Book
└── Chunk[]
    └── Content
```

Контент может быть представлен:

- готовым HTML;
- массивом структурированных блоков;
- комбинацией этих подходов.

Минимальные типы блоков первого этапа:

```text
Heading
Paragraph
```

Позже могут появиться:

```text
Image
List
Quote
CodeBlock
Table
Footnote
PageBreak
```

Чанк — техническая единица хранения и загрузки. Он не обязан соответствовать визуальной странице.

Один чанк может содержать:

- часть главы;
- целую главу;
- несколько глав;
- произвольный последовательный диапазон книги.

---

## 4. Визуальная страница

В проекте используется термин **страница** или **визуальная страница**.

Визуальная страница — это часть непрерывного контента, которая отображается в пределах одного viewport при текущих настройках чтения.

Она зависит от:

- ширины области чтения;
- высоты области чтения;
- размера шрифта;
- семейства шрифта;
- межстрочного интервала;
- отступов;
- стилей заголовков и других элементов;
- правил переноса слов;
- доступности и метрик загруженного шрифта.

Поэтому визуальная страница не является постоянной частью книги.

Один и тот же текст будет разбит на разное количество страниц:

- на телефоне и планшете;
- в портретной и альбомной ориентации;
- при разных размерах шрифта;
- при разных межстрочных интервалах.

---

## 5. Рабочая гипотеза пагинации

На первом этапе не предполагается вручную вычислять границы каждой страницы по словам, символам или DOM-узлам.

Вместо этого планируется использовать браузерный механизм **CSS Multi-column Layout**.

Контент рендерится как один непрерывный вертикальный поток, но контейнер имеет ограниченную высоту. Браузер автоматически переносит не поместившийся по высоте контент в следующую колонку.

Колонки располагаются горизонтально и воспринимаются как страницы:

```text
┌───────────────┐ gap ┌───────────────┐ gap ┌───────────────┐
│   страница 1  │     │   страница 2  │     │   страница 3  │
│               │     │               │     │               │
└───────────────┘     └───────────────┘     └───────────────┘
```

Концептуально раскладка строится так:

```text
HTML / Content blocks
        ↓
браузерный layout
        ↓
CSS columns
        ↓
горизонтальная последовательность страниц
```

Внешний viewport скрывает все колонки, кроме текущей:

```text
Reader viewport
└── overflow: hidden
    └── paginated content
        ├── column 0
        ├── column 1
        ├── column 2
        └── ...
```

Переход между страницами выполняется горизонтальным смещением общего полотна.

---

## 6. Основание для выбранного подхода

В изученном примере Яндекс Книг контент главы остаётся одним большим HTML-фрагментом:

```html
<h2>...</h2>
<p>...</p>
<ul>...</ul>
<p>...</p>
```

На контейнере применяются параметры наподобие:

```css
column-width: 745px;
column-gap: 40px;
transform: translateX(-3925px);
```

Это указывает на следующую схему:

1. HTML главы рендерится одним непрерывным потоком.
2. Браузер разбивает поток на CSS-колонки.
3. Каждая колонка выступает визуальной страницей.
4. Текущая страница выбирается горизонтальным смещением контейнера.

В исходном HTML также используются правила, помогающие браузеру выбирать места разрыва:

```css
page-break-inside: avoid;
page-break-before: auto;
page-break-after: auto;
```

Для современного CSS могут дополнительно использоваться:

```css
break-inside: avoid;
break-before: column;
break-after: avoid-column;
```

Таким образом, браузер берёт на себя наиболее сложную часть задачи:

- расчёт переносов строк;
- реальные метрики шрифта;
- высоту текста;
- разрыв абзацев;
- размещение заголовков;
- размещение списков и изображений;
- перераскладку при изменении viewport.

---

## 7. Пример базовой конфигурации раскладки

Концептуально используются два контейнера.

### Viewport

Отвечает за видимую область:

```css
.reader-viewport {
    width: var(--page-width);
    height: var(--page-height);
    overflow: hidden;
}
```

### Контейнер контента

Отвечает за горизонтальную колонную раскладку:

```css
.paginated-content {
    height: var(--page-height);
    column-width: var(--page-width);
    column-gap: var(--page-gap);
    column-fill: auto;
}
```

`column-fill: auto` нужен, чтобы браузер последовательно заполнял колонку сверху вниз и затем переходил к следующей, а не пытался равномерно балансировать контент между колонками.

Текущая страница выбирается смещением:

```text
pageOffset = pageIndex × pageStep
pageStep = pageWidth + pageGap
```

```css
transform: translateX(calc(-1 * var(--page-offset)));
```

Это описание является рабочей моделью. Точное поведение CSS Columns и формулу количества страниц необходимо подтвердить прототипом в целевых браузерах.

---

## 8. Что представляет собой страница в модели приложения

При таком подходе страницу не требуется хранить как копию текста или отдельный HTML-фрагмент.

Минимальная модель визуальной страницы:

```text
Page
- index
- chunkId
```

Для навигации внутри уже разложенного чанка достаточно:

```text
currentPageIndex
pageCount
pageWidth
pageHeight
pageGap
```

Однако индекс страницы нельзя считать устойчивой позицией в книге.

Например, после увеличения шрифта страница `12` будет содержать уже другой участок текста.

Поэтому нужно различать:

### Визуальное состояние

```text
chunkId
pageIndex
pageCount
```

### Логическую позицию чтения

```text
chunkId
blockId / elementId
offset
```

Логическая позиция должна ссылаться на исходный контент, а не на результат текущей визуальной раскладки.

---

## 9. Чанки и пагинация

Чанк — единица загрузки.

Страница — единица отображения.

Один чанк может образовать несколько визуальных страниц:

```text
Chunk A
├── Page 0
├── Page 1
├── Page 2
└── Page 3
```

Базовая навигация:

```text
next page:
    если текущая страница не последняя
        перейти на следующую страницу чанка
    иначе
        загрузить следующий чанк
        перейти на его первую страницу
```

```text
previous page:
    если текущая страница не первая
        перейти на предыдущую страницу чанка
    иначе
        загрузить предыдущий чанк
        перейти на его последнюю страницу
```

---

## 10. Граница между чанками

Если каждый чанк рендерится в отдельном колонном контейнере, его последняя страница может остаться частично пустой.

Начало следующего чанка при этом не продолжит текущую страницу автоматически.

Возможные стратегии:

### Стратегия A — новый чанк с новой страницы

Каждый чанк всегда начинается с отдельной визуальной страницы.

Преимущества:

- простая реализация;
- простая загрузка;
- понятная навигация;
- легко удалять старые чанки из DOM.

Недостатки:

- возможна лишняя пустота в конце чанка;
- технические границы загрузки становятся видимыми читателю.

### Стратегия B — несколько чанков в одном потоке

Текущий и соседние чанки рендерятся в одном колонном контейнере.

Преимущества:

- непрерывная раскладка;
- следующая страница заполняется началом следующего чанка;
- границы загрузки не видны читателю.

Недостатки:

- сложнее считать страницы отдельных чанков;
- сложнее добавлять и удалять контент из начала потока;
- при добавлении предыдущего чанка могут изменяться индексы колонок;
- сложнее сохранять визуальную стабильность.

### Стратегия C — крупные семантические чанки

В качестве чанка используется глава или другой естественный раздел книги.

Преимущества:

- пустое место в конце главы может восприниматься нормально;
- простая модель;
- структура книги совпадает с единицами загрузки.

Недостатки:

- главы могут сильно отличаться по размеру;
- отдельные чанки могут оказаться слишком большими.

На первом прототипе разумно начать со стратегии A или C и отдельно проверить, насколько заметна пустота на реальных книгах.

---

## 11. Позиция чтения

Позицию чтения нельзя надёжно сохранять только как номер страницы.

Нужно сохранять locator, привязанный к исходному контенту.

Возможная модель:

```text
ReadingPosition
- bookId
- chunkId
- elementId
- offset
```

Где:

- `chunkId` определяет загруженный фрагмент;
- `elementId` определяет блок или HTML-элемент;
- `offset` уточняет позицию внутри текстового содержимого.

В приложенном примере HTML многие элементы уже имеют стабильные `id`. Это потенциально позволяет использовать идентификатор элемента как основу locator.

После изменения раскладки:

1. загружается нужный чанк;
2. находится целевой элемент;
3. определяется колонка, в которую попал элемент;
4. эта колонка становится текущей страницей.

Точный способ определения текущего элемента и смещения требует отдельного эксперимента.

---

## 12. Перерасчёт раскладки

Пагинация должна пересчитываться при изменении:

- ширины viewport;
- высоты viewport;
- ориентации устройства;
- размера шрифта;
- семейства шрифта;
- межстрочного интервала;
- внешних и внутренних отступов;
- режима отображения;
- содержимого чанка;
- состояния загруженных изображений;
- состояния загруженных web fonts.

Процесс перераскладки:

```text
1. Зафиксировать логическую позицию чтения.
2. Изменить параметры отображения.
3. Дождаться завершения layout.
4. Пересчитать количество колонок.
5. Найти колонку сохранённой логической позиции.
6. Показать найденную колонку.
```

Важно дождаться загрузки шрифтов и изображений, иначе после первого измерения layout может измениться повторно.

---

## 13. Ответственность браузера и ядра

### Браузер отвечает за

- переносы строк;
- высоту текста;
- разрыв контента между колонками;
- метрики шрифтов;
- размещение HTML-элементов;
- применение CSS-правил разрыва;
- физическую раскладку страниц.

### Reader Core отвечает за

- текущий чанк;
- текущий индекс страницы;
- переход вперёд и назад;
- получение соседних чанков;
- количество страниц в разложенном контенте;
- сохранение логической позиции;
- восстановление позиции после перераскладки;
- состояние загрузки;
- обработку начала и конца книги.

### UI-слой отвечает за

- создание и измерение viewport;
- рендеринг HTML или блоков;
- применение настроек чтения;
- выполнение DOM-измерений;
- анимацию переходов;
- пользовательские жесты;
- панели управления.

Граница между Reader Core и UI пока требует дополнительного проектирования, поскольку расчёт колонок основан на DOM и не может быть полностью независимым от браузера.

---

## 14. Offline-first направление

В дальнейшем Reader должен поддерживать локальное чтение без сети.

Потенциально локально сохраняются:

- метаданные книги;
- оглавление;
- чанки книги;
- ресурсы книги;
- обложка;
- позиция чтения;
- пользовательские настройки;
- закладки.

Визуальные страницы сохранять как постоянные данные не требуется, поскольку они зависят от текущего viewport и настроек отображения.

Допустимо кэшировать результат раскладки только как временную оптимизацию для конкретной конфигурации:

```text
layoutKey =
    chunkId
    + viewportWidth
    + viewportHeight
    + fontFamily
    + fontSize
    + lineHeight
    + margins
```

Но источник истины — контент и логическая позиция, а не массив рассчитанных страниц.

## 15. Первый технический прототип

Цель первого прототипа — проверить жизнеспособность пагинации через CSS Columns.

Минимальный сценарий:

1. Взять один большой HTML-чанк.
2. Отобразить его в контейнере фиксированной ширины и высоты.
3. Включить горизонтальные CSS-колонки.
4. Определить фактическое количество колонок.
5. Реализовать переход между ними.
6. Проверить отсутствие вертикального скролла.
7. Изменить размер viewport.
8. Изменить размер шрифта.
9. Убедиться, что контент перераскладывается.
10. Попробовать восстановить приблизительно ту же позицию текста.

Первый прототип не обязан сразу поддерживать:

- несколько чанков;
- offline;
- сохранение в базе;
- сложные изображения;
- таблицы;
- сноски;
- выделения;
- анимацию свайпа.

---

## 16. Критерии успешности первого прототипа

Прототип можно считать успешным, если:

- длинный HTML автоматически разбивается на горизонтальные страницы;
- текст не выходит за вертикальные и горизонтальные границы viewport;
- строки не обрезаются посередине по горизонтали;
- переход между страницами происходит без вертикального скролла;
- можно определить количество страниц;
- изменение размера окна вызывает корректную перераскладку;
- изменение размера шрифта вызывает корректную перераскладку;
- заголовки, списки и обычные абзацы отображаются приемлемо;
- навигация не требует копирования текста в отдельные page-объекты;
- на реальных чанках производительность остаётся приемлемой.

## 17. Основные риски и открытые вопросы

### Расчёт количества страниц

Нужно проверить, насколько стабильно количество колонок определяется через `scrollWidth`, ширину страницы и gap в разных браузерах.

### DOM-измерения

Необходимо выбрать надёжный способ определить:

- колонку конкретного элемента;
- элемент в начале текущей страницы;
- элемент в конце текущей страницы;
- текущую логическую позицию пользователя.

### Перераскладка

После загрузки шрифта, изображения или динамического контента ширина полотна может измениться.

### Большие HTML-чанки

Нужно измерить:

- время первичного layout;
- потребление памяти;
- стоимость изменения размера шрифта;
- влияние количества DOM-элементов;
- предел разумного размера чанка.

### Разрывы элементов

Нужно проверить реальное поведение:

- заголовков;
- изображений;
- списков;
- таблиц;
- цитат;
- сносок;
- очень длинных неразрывных фрагментов.

### Различия браузеров

CSS Multi-column Layout может иметь различия в:

- Chromium;
- WebKit;
- Firefox;
- мобильных WebView.

### Последняя страница чанка

Нужно решить, должна ли следующая часть книги продолжать свободное место или начинаться с новой страницы.

### Стабильность позиции

Нужно определить формат locator, который переживает:

- смену размера шрифта;
- смену экрана;
- изменение HTML;
- обновление версии книги.

## 18. Текущая архитектурная гипотеза

```text
Content Source
    ↓
Chunk Loader
    ↓
Content Renderer
    ↓
Browser Column Layout
    ↓
Pagination Adapter
    ↓
Reader Core
    ↓
Reader UI
```

### Content Source

Предоставляет метаданные и чанки книги.

### Chunk Loader

Загружает текущий, предыдущий и следующий чанки.

### Content Renderer

Преобразует данные чанка в HTML/DOM.

### Browser Column Layout

Выполняет физическую раскладку текста по визуальным страницам.

### Pagination Adapter

Считывает результат DOM-layout и предоставляет ядру абстрактные операции:

```text
getPageCount()
getCurrentPage()
goToPage(index)
findPageByLocator(locator)
getLocatorForPage(index)
```

### Reader Core

Управляет состоянием чтения и переходами между чанками.

### Reader UI

Отображает книгу и обрабатывает действия пользователя.

## 19. Главный принцип проекта

> Контент книги хранится как непрерывный логический поток. Визуальные страницы вычисляются браузером для текущей конфигурации отображения и не являются самостоятельными копиями контента.

Иными словами:

```text
content + layout configuration → visual pages
```

Страницы — временный результат раскладки.

Позиция чтения должна быть привязана к исходному контенту.

Чанк является единицей загрузки, но не обязан становиться единицей визуального отображения.

## 20. Ближайший следующий шаг

Создать минимальный браузерный эксперимент на одном реальном HTML-чанке и проверить:

1. корректную горизонтальную раскладку через CSS Columns;
2. точный расчёт количества страниц;
3. переход через `transform`;
4. перераскладку при resize;
5. восстановление позиции после изменения размера шрифта;
6. поведение на границах заголовков, списков и изображений.

Только после этого имеет смысл окончательно проектировать API пагинационного ядра.
